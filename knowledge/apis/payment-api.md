# Payment API

## Purpose

The Payment API provides secure REST-based interfaces for initiating, authorizing, capturing, reversing, and querying payment transactions processed by the Mercury Payments platform. It serves as the standard integration layer for internal banking applications, merchant services, partner systems, and digital channels while enforcing enterprise security, auditing, and compliance requirements.

---

## Business Overview

The Payment API is a core component of the Mercury Payments platform and supports digital banking, merchant onboarding, payment authorization, settlement processing, and transaction reconciliation. The API is designed as a stateless service with high availability, enabling secure transaction processing across multiple business domains.

All production integrations must comply with the standards defined in **integration-guidelines.md** and operational procedures documented in **../operations/incident-management.md**.

---

## API Architecture

The Payment API follows RESTful design principles and communicates over HTTPS using JSON payloads. Authentication is delegated to the Orion Identity platform through OAuth 2.0 access tokens.

Primary components include:

- API Gateway
- Payment Service
- Authorization Engine
- Transaction Database
- Merchant Registry
- Token Vault
- Event Publishing Service

Business events generated by the API are published to the enterprise event bus as described in **event-catalog.md**.

---

## Authentication

All requests require:

- OAuth 2.0 Bearer Token
- TLS 1.2 or higher
- Valid client registration
- Required API scopes

Example Authorization Header

```http
Authorization: Bearer eyJhbGciOi...
```

Authentication services are provided by **Orion Identity** and documented in **identity-api.md**.

---

## Core REST Endpoints

| Method | Endpoint | Description |
|---------|----------|-------------|
| POST | /api/v1/payments | Create a payment |
| GET | /api/v1/payments/{paymentId} | Retrieve payment details |
| POST | /api/v1/payments/{paymentId}/capture | Capture an authorized payment |
| POST | /api/v1/payments/{paymentId}/refund | Process a refund |
| POST | /api/v1/payments/{paymentId}/cancel | Cancel a payment |
| GET | /api/v1/payments/status | Payment health and status |

---

## Sample Request

```http
POST /api/v1/payments
Content-Type: application/json
Authorization: Bearer <access_token>
```

## Error Handling

The API returns standardized HTTP status codes and structured error responses.

| Status | Description |
|---------|-------------|
| 200 | Successful request |
| 201 | Resource created |
| 400 | Invalid request |
| 401 | Authentication failed |
| 403 | Authorization denied |
| 404 | Resource not found |
| 409 | Duplicate transaction |
| 429 | Rate limit exceeded |
| 500 | Internal server error |
| 503 | Service unavailable |

Example Error Response

```json
{
  "errorCode": "PAYMENT_NOT_FOUND",
  "message": "The requested payment could not be located.",
  "correlationId": "c18df4b7"
}
```

## Rate Limiting

To ensure platform stability, API requests are subject to enterprise rate limits.

Default limits include:

- 500 requests per minute per client
- Burst capacity for approved enterprise integrations
- Dynamic throttling during peak demand
- Automatic protection against abusive traffic

Rate limit thresholds may vary based on integration agreements and business criticality.

---

## Security Considerations

The Payment API enforces enterprise security controls including:

- OAuth 2.0 authentication
- TLS encryption
- Role-based authorization
- Tokenized payment data
- Request validation
- Input sanitization
- Audit logging
- Correlation ID tracking

Sensitive information such as Primary Account Numbers (PAN), CVV values, authentication credentials, and cryptographic secrets must never be transmitted or stored in plaintext.
